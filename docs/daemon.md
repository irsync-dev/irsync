# Running the irsync daemon

`irsync daemon` runs in the foreground and never daemonises itself; let
systemd or launchd supervise it. It needs no setup beyond `irsync export add`
(see the [README](../README.md)).

## Files

All under `~/.config/irsync/`, all optional, each overridable on the command
line:

| File | Flag | Holds |
| --- | --- | --- |
| `irsync.toml` | `--config` | settings; the daemon reads the `[daemon]` tables and the top-level `state_dir` |
| `hosts.toml` | `--hosts` | aliases for clients (and for servers, when this machine is also a client) |
| `exports.toml` | `--exports` | the exports and who may use them |
| `daemon_ed25519` (+ `.pub`) | `[daemon] identity` | the daemon's identity, generated if missing |

There is no `/etc` lookup: a system-wide daemon passes the three paths
explicitly (see [A system-wide daemon](#a-system-wide-daemon) below). `irsync id show --daemon` prints
the daemon's public key line and `EndpointId` (the id alone is its last
line), generating the identity first if it does not exist yet. `irsync
export add` and `irsync show` print the id too.

## Changing exports while it runs

The daemon reads `hosts.toml` and `exports.toml` afresh on every accepted
connection, after the handshake has proved the peer's `EndpointId`. `irsync
export add`/`remove`, `grant add`/`remove` and `host add`/`remove` therefore
take effect on the next connection, with no restart. A `grant remove` or
`export remove` does not end a session already in progress; it refuses only
new connections. The commands
write the files
atomically. If either file cannot be read or parsed, the daemon logs the error
at `warn`, rejects that connection and keeps running: it fails closed and does
not fall back to an earlier copy. A missing file counts as empty. At startup an
`exports.toml` that does not parse is fatal. A grant entry that is neither a
known alias nor an `EndpointId` matches nobody and is logged.

A daemon with no exports starts, logs a warning naming the exports file, and
serves nothing until `irsync export add` creates one.

A client whose key is not granted anything is closed on before any protocol
message is read. The client reports that the daemon rejected its key and
prints the exact `irsync grant add <export> <id>` line to run on the daemon's
machine; the daemon's log shows `rejecting unauthorized key` with the first
ten hex digits of the peer's id.

Settings in `irsync.toml` (`listen`, relays, discovery, `idle_timeout`, ...)
are read once and need a restart.

### Indexes

An export's index is opened, and its hourly collection and `warm_index`
warm-up started, when the export is first used: at startup for exports already
in the file, on the first connection naming it for one added later. Exports
with the same path share an index. A removed export cannot be connected to,
but keeps its index and collection task until the daemon restarts. Changing
`warm_index` on a running export takes effect at restart.

## A system-wide daemon

A daemon run by the service manager as its own account (`irsync` below) keeps
everything in one directory, here `/etc/irsync/` (`/usr/local/etc/irsync/` on
macOS). Its `irsync.toml` names the identity and the state directory, which
would otherwise default to that account's home:

```toml
state_dir = "/var/lib/irsync"

[daemon]
identity = "/etc/irsync/daemon_ed25519"
```

The management commands edit whatever files they are given, and without
flags those are the ones in your own `~/.config/irsync/`: there `irsync
export add` would write your `exports.toml` and generate a stray
`~/.config/irsync/daemon_ed25519`, and print that key's id as "the daemon's".
Run them as the daemon's account, with the same three paths the daemon gets
(for `host`, `export` and `grant` the flags go anywhere after the noun):

```sh
F="--config /etc/irsync/irsync.toml --hosts /etc/irsync/hosts.toml --exports /etc/irsync/exports.toml"
sudo -u irsync irsync export add photos:/srv/photos $F
sudo -u irsync irsync grant add photos laptop $F
sudo -u irsync irsync host add laptop <id> $F
sudo -u irsync irsync id show --daemon $F
sudo -u irsync irsync show $F
```

Running them as `irsync` keeps the files owned by the account that reads
them: the commands replace a file by writing a new one next to it and
renaming it, so `/etc/irsync/` must be writable by `irsync` (for example
`install -d -o irsync -g irsync -m 0755 /etc/irsync`), and a daemon key
generated by root would be mode 0600 and unreadable by the daemon. Root can
run the same commands with the same flags if it then fixes the ownership.
`irsync show` and `irsync id show --all` also load (and, if missing, generate) the
client identity named by `identity` in the same `irsync.toml`.

## systemd (Linux)

`/etc/systemd/system/irsync.service`:

```ini
[Unit]
Description=irsync daemon
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
ExecStart=/usr/local/bin/irsync daemon --config /etc/irsync/irsync.toml --hosts /etc/irsync/hosts.toml --exports /etc/irsync/exports.toml
Restart=on-failure
RestartSec=5
User=irsync
Environment=RUST_LOG=info

[Install]
WantedBy=multi-user.target
```

The `User=` account needs read access to the export paths (write access for
read-write exports), to the identity key and the three config files, and write
access to `state_dir`; manage the exports as described in
[A system-wide daemon](#a-system-wide-daemon). Then `systemctl enable --now irsync` and
`journalctl -u irsync -f`.

**Do not run the daemon as root.** A receiving daemon applies the archive
metadata the client sends (permissions, owner, group, device nodes): as root
that means any client with write access to an export can create setuid files
owned by root, files owned by other users, and device nodes in it. Run it as a
dedicated unprivileged account (`irsync` above) that owns the export trees;
ownership is then applied only where that account may (its own groups), as
rsync does without privilege.

## launchd (macOS)

`~/Library/LaunchAgents/net.irsync.daemon.plist` (use `/Library/LaunchDaemons`
for a system-wide daemon, with a `UserName` key naming its account and the
management commands run as in [A system-wide daemon](#a-system-wide-daemon),
with the `/usr/local/etc/irsync/` paths):

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key>
  <string>net.irsync.daemon</string>
  <key>ProgramArguments</key>
  <array>
    <string>/usr/local/bin/irsync</string>
    <string>daemon</string>
    <string>--config</string>
    <string>/usr/local/etc/irsync/irsync.toml</string>
    <string>--hosts</string>
    <string>/usr/local/etc/irsync/hosts.toml</string>
    <string>--exports</string>
    <string>/usr/local/etc/irsync/exports.toml</string>
  </array>
  <key>EnvironmentVariables</key>
  <dict>
    <key>RUST_LOG</key>
    <string>info</string>
  </dict>
  <key>RunAtLoad</key>
  <true/>
  <key>KeepAlive</key>
  <true/>
  <key>StandardErrorPath</key>
  <string>/usr/local/var/log/irsync.log</string>
</dict>
</plist>
```

Load it with `launchctl load ~/Library/LaunchAgents/net.irsync.daemon.plist`.

## Logging

Logs go to stderr (journald and the launchd `StandardErrorPath` capture it).
The default level is `info`; `-v` raises it to `debug`, `-vv` to `trace`, and
`RUST_LOG` (standard `tracing` filter syntax, e.g. `RUST_LOG=irsync=debug`)
overrides both.

## Idle connections

`idle_timeout` (default `"30m"`; a number of seconds or a duration string such
as `"90s"`, `"30m"`, `"2h"`) is how long an authenticated session may go
without activity before the daemon drops its connection; the client then
reconnects and resumes. Activity is any control message or file data on the
wire, and also local progress on either side: chunks written or copied,
hashing (bumped every 64 MiB of a large file), finalizing (the `sync` and
whole-file re-hash of a large `.part`), and each deletion. Set
`idle_timeout = "0"` to disable the limit.

A connection dropped while a large file is being finalized does not fail that
file: the resumed session waits up to 60 s for the earlier connection's
finalize to release the `.part` file before reporting it busy.

## State directory and garbage collection

`state_dir` (default `~/.local/state/irsync`) holds one SQLite index per export
under `index/`: cached file hashes, partial-file progress and the daemon's
session records. It is safe to delete; the next sync rebuilds it, at the cost
of re-hashing and of losing resumable sessions.

An export filled by something other than irsync (a prior rsync, a restore)
contributes nothing to rename detection and chunk reuse until its files are
hashed. `warm_index = true` on an export hashes them in the background when
the daemon starts (only files whose index row is not fresh are read, so a
restart is cheap); `irsync export update NAME...|all` does the same on
demand, and a session hashes destination files of the size of a
file it is about to fetch on its own.

Interrupted transfers leave `.irsync.<name>.part` files next to their
destinations. The daemon checks each export once an hour (first check a minute
after start) and walks it only when its last collection is a day old or
partial-file records older than `dormant_session_timeout` exist; it collects:

- partial-file records and `.irsync.*.part` files untouched for longer than
  `dormant_session_timeout`, unless a stored session still lists the file;
- dormant sessions not touched for `dormant_session_timeout`.

A failure to remove one file is logged and reported, and the pass carries on.
Partial-file records do not remember a `--partial-dir`: a stale record whose
`.part` file is not next to its destination is simply dropped (reported as a
record without a file), and the file itself, if it exists, is collected on a
later pass as an orphan by its age.

`dormant_session_timeout` defaults to 7 days (a number of seconds, or a
duration string as in the config). A live transfer is never affected: its
partial record is refreshed as chunks arrive and its session lists its files.
Only regular files named exactly `.irsync.<name>.part` are ever removed;
symlinks are never followed. Each run logs a summary at `info`. On a client,
`irsync gc` does the same for all local roots (add `-n` to only list).

## Relays, DHT and discovery

The daemon publishes its address so clients can find it by `EndpointId`:
`[daemon.discovery] dns` uses n0's pkarr/DNS service, `dht` the mainline DHT, and `mdns` the local
network. Clients resolve with the same mechanisms (`--no-dht` or a host's `dht` and `mdns` keys
turn lookups off on their side).

Connections start through a relay and upgrade to a direct path when hole
punching succeeds. Relays are a fallback and much slower than a direct path.
Set `[daemon] relay = "https://..."` to use your own relay, or
`relay_mode = "disabled"` for direct-only operation.

- Published DHT records carry relay-only addresses. With relays disabled they
  would carry none, so the daemon logs a warning if `dht` is on while
  `relay_mode = "disabled"`.
- Users behind a symmetric NAT (many mobile and carrier-grade NATs) on both
  ends cannot hole-punch and stay on the relay. For them we recommend a
  self-hosted relay near the daemon (iroh ships `iroh-relay`), set as `relay`
  in the daemon config and as `relay` in the client's `hosts.toml` table (or
  `--relay`), instead of depending on the shared public relays.

### Isolated operation (localhost, LAN, no internet)

For two irsync processes on one machine or one LAN, or anywhere without
internet access, neither side needs relays or lookups. Note that `listen`
alone only pins sockets; it does not isolate the daemon. The isolated daemon
turns everything off explicitly:

```toml
[daemon]
listen = ["127.0.0.1:0"]   # at most one IPv4 and one IPv6 entry; port 0 = daemon picks
relay_mode = "disabled"
portmap = false            # no UPnP/PCP/NAT-PMP gateway probing

[daemon.discovery]
dht = false
dns = false
mdns = false
```

`--listen ADDR` on the command line replaces the config's `listen` list. On
startup the daemon prints its id and, with the real ports, one line per
bound socket, on stdout; a parent process reads these two kinds of line and
can dial at once:

```
endpoint id: <id>
listening on: 127.0.0.1:43210
```

The client dials directly when given at least one address, in the host's
`address` key or with `--address ADDR` (repeatable; `ip:port`, `[ipv6]:port` or
`host:port`, hostnames resolved with the system resolver):

```toml
[hosts.local]
endpoint_id = "<id>"
address = ["127.0.0.1:43210"]
```

```sh
irsync -a --address localhost:43210 ./src <id>:data/
```

Giving an address (`irsync host add local <id> --address 127.0.0.1:43210` writes the table above) turns the client's relay, n0 DNS, DHT, mDNS and port
mapper off: it talks to nothing but the addresses it was given. The daemon's
EndpointId is still required and still verified; `--address` together with
`--relay` is refused. iroh may still learn and probe further addresses of
the daemon itself over the connection; against a loopback daemon those are
loopback too.
