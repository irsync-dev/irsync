# Release branches and tag-last releases

Date: 2026-11-15

## Intent

Two changes to how irsync is released.

**1. The tag comes last.** Today a release starts when someone pushes a
`v*` tag. The tag rules make every `v*` tag permanent, so if the release
fails after the push (a failing test, a wrong version in a file), that
version number is used up and the next release has to skip it. That already
happened: `v0.1.0-alpha.1` and `v0.1.0-alpha.2` are tags with no release.
For alphas and betas that is an odd look. For stable releases, which users
see in Homebrew, apt and dnf, it is not acceptable: users would see 1.2.0
missing between 1.1.x and 1.2.1.

The fix is to stop using the tag as the trigger. A release is started by a
workflow run that is given the version. It checks, tests and builds without
any tag existing. The tag and the GitHub Release are created together, as
the last step before anything is public. A failure before that leaves no
tag, and the same number can be tried again.

**2. Stable releases come from release branches.** Today every release is
cut from `main`, so a fix for a released version can only ship together
with whatever else has landed on `main` since. We want to be able to ship
1.2.1 holding only a fix, while `main` carries unfinished work for 1.3.

## Goals

- A failed release that has not yet created its GitHub Release leaves no
  tag behind. Running the release again with the same version works.
- Release tags (`v*`) are only ever created by the release workflow.
  Ideally GitHub refuses a hand-pushed tag; if that isn't possible without
  editing `release.yml`, a hand-pushed tag is caught instead (see
  "Blocking or catching hand-pushed tags" below).
- When `X.Y.0` is released, a branch `release-X.Y` is created at the
  released commit. Every later `X.Y.Z` stable release is cut from that
  branch.
- A fix lands on `main` first (through a PR, as today) and is then copied
  down to `release-X.Y` with `git cherry-pick`, through a PR into that
  branch, with CI.
- `release-X.Y` branches are protected like `main`: changes only through a
  PR, the `CI result` check must pass, no force push, no deletion.
- Everything the current release does still happens: the full test suite
  (including the musl release targets) on the exact commit that is
  released, the same platforms and artifacts, attestations, immutable
  releases, packages and Homebrew after approval of the `release`
  environment, release notes, and a way to finish a release whose later
  steps failed (today's resume workflow).
- The release docs (`book/src/contributing/releasing.md`) describe the new
  process, including the bug-fix release.

## Non-goals

- Supporting more than one stable line at a time. Once 1.3.0 is out,
  `release-1.2` gets no more releases. (The process doesn't have to stop
  you, but nothing is built for it.)
- Automating the cherry-pick from `main` to a release branch.
- Recovering a version number after the GitHub Release was created. From
  that point the release is public and immutable; failures in packages,
  Homebrew or notes are finished with the resume workflow, as today.
- Changing which platforms are built or what gets published.

## Anti-goals

These would make the change a failure even if it otherwise works.

- **A tag on a commit that wasn't tested.** The tag must point at exactly
  the commit the full test suite passed on, even if someone pushes to the
  branch while the tests run.
- **A tag without a GitHub Release, or a release without a tag.** They are
  created together or not at all.
- **Any path that publishes without the full test suite.** As today,
  `release.yml` must never be launched by hand.
- **Weakening the tag protection.** Tags still can't be moved or deleted by
  anyone, admins included. The only possible new exception is that the
  release workflow may *create* them.
- **Editing `release.yml` by hand.** It stays generated by `dist generate`;
  changes go through `dist-workspace.toml`.

## Decided

These were decided in the conversation.

- Tag last, as described above.
- Release branches named `release-X.Y`, created when `X.Y.0` is cut, and
  all `X.Y.Z` stable releases cut from them.
- Fixes go to `main` first and are copied down.
- Hand-pushed `v*` tags are blocked; only the workflow creates them. If
  GitHub can't block them while `release.yml` stays untouched, keeping
  `release.yml` untouched wins, and stray tags are caught instead of
  blocked. No GitHub App, no patching of the generated file.

## How it fits the current workflows

What exists today (see `book/src/contributing/releasing.md`):

- `release-gate.yml` runs on a pushed `v*` tag: check, test (calls
  `ci.yml`), launch `release.yml` and wait, then packages and Homebrew (in
  the `release` environment, after approval) and notes.
- `release.yml` is generated by cargo-dist 0.34.0 with
  `dispatch-releases = true`. It takes the tag as a text input and ends
  with `gh release create "<tag>" --target "$RELEASE_COMMIT"`, where
  `RELEASE_COMMIT` is `github.sha` of the `release.yml` run. If the tag
  doesn't exist, that command creates it there, together with the release.
  This is what makes tag-last possible without editing `release.yml`.
- `release-resume.yml` is started by hand on the tag and runs packages,
  Homebrew and notes for an existing release.
- `tools/github_settings.py` sets the `Release tags` ruleset (no update, no
  deletion, no force push, no bypass) and the `release` environment, which
  only opens for runs on a `v*` tag.
- `.github/scripts/bump-version.sh` makes a `Release vX.Y.Z` commit on a
  branch `release-vX.Y.Z` for a PR into `main`.

### The new flow

1. **Bump.** The version commit goes through a PR, as today. For a
   pre-release or an `X.Y.0`, into `main`. For a patch `X.Y.Z` (Z > 0),
   into `release-X.Y`. The bump script picks the base branch from the
   version.
2. **Start.** The maintainer runs the release workflow (Actions tab or
   `gh workflow run`) with the version as input. The source branch follows
   from the version: pre-releases and `X.Y.0` from `main`, `X.Y.Z` patches
   from `release-X.Y`.
3. **Check.** Version name is valid (same rules as
   `check-release-tag.sh`), the files on the source branch hold that
   version, the tag doesn't exist yet, and for `X.Y.0` that `release-X.Y`
   doesn't exist yet. Takes seconds.
4. **Test.** The full suite (`ci.yml` with the release targets) on the
   branch's commit at that moment. That commit is what gets released.
5. **Release.** `release.yml` builds that commit and creates the tag and the
   GitHub Release together. This is the point of no return.
6. **Branch.** For `X.Y.0`, create `release-X.Y` at the released commit.
7. **Packages, Homebrew, notes** for stable releases, after approval, as
   today. Notes for all.

Running the workflow again after a failure in steps 3 to 5 (before the
GitHub Release exists) just works. After step 5, the check refuses because
the tag exists, and the resume workflow finishes the release.

## Open problems for the builder

These need solving; the approach is left to you, within the anti-goals.

- **Pinning `release.yml` to the tested commit.** `release.yml` tags
  `github.sha` of its own run. Launched on a branch, that is the branch tip
  at launch time, which may be newer than the tested commit. The gate today
  checks the launched run's `headSha` and cancels on a mismatch; that alone
  would turn a push during the tests into a failed release. Better: launch
  `release.yml` on a ref that can only point at the tested commit, for
  example a short-lived branch the workflow creates at that commit and
  deletes afterwards. Whatever you choose, the tag must end up on the tested
  commit.
- **Blocking or catching hand-pushed tags.** The tag is created inside
  `release.yml` by `gh release create`, which always runs with that run's
  own built-in `GITHUB_TOKEN`. Nothing outside `release.yml` can hand it a
  different token.
  - **First try the hard block.** Add a "restrict creations" rule for
    `refs/tags/v*` with the workflow's built-in token as the only exception,
    while update, deletion and force push keep no exception at all.
    Rulesets apply a bypass to the whole ruleset, so this probably means two
    rulesets. Check GitHub's current docs, then prove it with a real alpha
    release.
  - **If GitHub won't accept the built-in token as the exception**, leave
    tag creation open and catch stray tags instead. Do not add a GitHub App
    and do not patch `release.yml`. A pushed tag no longer starts anything,
    so a stray tag can't release anything; at worst it uses up a number.
    Catch it in two places: the release workflow refuses to go on if a `v*`
    tag exists that it didn't create (for example, one with no GitHub
    Release behind it, other than the two old alpha tags), and
    `tools/github_settings.py check` (or a similar check) reports such tags.
    The docs say plainly that tags are never pushed by hand.
  - Either way, `tools/github_settings.py check` must report the new
    settings.
- **The `release` environment.** It only opens on `v*` tag refs. In the new
  flow the gate runs on a branch. One way that keeps the secrets locked to
  tags: once the release exists, launch the packages, Homebrew and notes
  steps on the new tag, the way `release-resume.yml` already runs. Who may
  start the release workflow, and whether a stable release should need an
  approval before step 5, is your call; today anyone with write access can
  start the gate, and stable releases need an approval only for packages
  and Homebrew. Don't make that weaker.
- **Release branches and CI.** Check that `ci.yml` and the `CI result`
  required check run for PRs into `release-*` branches and for pushes to
  them, and add the branch ruleset to `tools/github_settings.py`.
- **Release notes.** For a stable release, the change list starts at the
  previous stable release. `.github/scripts/release-notes.sh` already picks
  that tag by version, which gives the right list for a patch from a
  release branch (1.2.1 lists what changed since 1.2.0). Keep it that way.

## Calls made without asking

Marked so they can be checked.

- The release workflow derives the source branch from the version, instead
  of taking a branch as a second input.
- Pre-releases always come from `main`. A `1.2.1-beta.1` from `release-1.2`
  is not supported.
- The bump PR branches are renamed from `release-vX.Y.Z` to
  `bump-vX.Y.Z`, so they can't be confused with `release-X.Y`.
- The tag-push trigger is removed completely, not kept alongside.
- `main` is not bumped automatically after `X.Y.0`; the next alpha's bump
  sets the new version, as today.

## Left to the builder

- Whether this stays one workflow (`release-gate.yml` reworked) or becomes
  a new one; naming.
- How the branch for `X.Y.0` is created and with which token.
- Script changes in `.github/scripts/`, and their tests in
  `.github/scripts/tests/`.
- How the docs are restructured, as long as `releasing.md` covers cutting a
  pre-release, an `X.Y.0`, a patch from a release branch, copying a fix
  down, and what to do when each step fails.
